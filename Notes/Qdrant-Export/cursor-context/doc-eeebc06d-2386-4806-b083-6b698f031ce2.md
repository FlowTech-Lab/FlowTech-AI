Professional Pull Request Template - Best Practices:

STANDARD STRUCTURE:
1. Title: Clear, descriptive with emoji (🚀 for features, 🐛 for bugs, 🔧 for fixes)
2. Overview: Brief summary of PR purpose, number of commits, main changes
3. What's Changed: Detailed breakdown by category (Accessibility, UI, Features, Bug Fixes, Documentation, etc.)
4. Statistics: Files modified, lines changed, tests added/updated
5. Commit Details: List all commits with descriptions
6. Testing: Manual tests performed, automated tests recommended
7. Impact: Compliance, UX, Development Experience, Maintenance
8. Notes: Important considerations, follow-ups needed
9. References: Links to related documentation, issues, ADRs
10. Migration Notes: Database changes, environment variables, dependencies, deployment notes

SECTIONS BEST PRACTICES:
- Use checkboxes (✅ ⏳) for completed/pending items
- Group related changes by category
- Include WCAG/standards references when applicable
- Specify breaking changes clearly
- Add deployment readiness status
- Include file counts and statistics
- Reference commit hashes for traceability

LANGUAGE:
- Always use English for professional PRs (industry standard)
- Be concise but comprehensive
- Use bullet points for readability
- Include technical details when relevant

EXAMPLES OF GOOD PR STRUCTURES:
- Feature PRs: Focus on functionality, user impact, testing
- Fix PRs: Problem description, solution, verification
- Documentation PRs: Structure changes, new content, organization
- Accessibility PRs: WCAG criteria, compliance level, audit results
- Release PRs: Migration notes, breaking changes, deployment steps

COMMON CATEGORIES:
- Accessibility (WCAG compliance)
- UI/UX improvements
- Bug fixes
- Features
- Documentation
- Development environment
- Dependencies
- Performance
- Security
- Testing

METADATA TO INCLUDE:
- Type (Feature/Fix/Enhancement/Documentation)
- Priority (Low/Medium/High/Critical)
- Breaking Changes (Yes/No/Partial)
- Tests status
- Deployment readiness

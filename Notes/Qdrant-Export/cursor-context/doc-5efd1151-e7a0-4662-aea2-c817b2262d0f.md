Découpage Script de Déploiement - Bonnes Pratiques 2025

Contexte: Les scripts de déploiement monolithiques (2700+ lignes) deviennent rapidement ingérables en production. Cette note documente les bonnes pratiques de modularisation pour améliorer la maintenabilité, la testabilité et la réutilisabilité des scripts de déploiement bash.

Problème - Symptômes d'un Script Monolithique:
- Maintenabilité difficile: Débugger une fonction nécessite de scroller 2700 lignes
- Testabilité impossible: Tester une fonction nécessite de sourcer tout le script + dépendances
- Duplication de code: Code dupliqué entre staging et production
- Performance dégradée: Tout le script parsé même si non utilisé (startup time 2s+)
- Sécurité limitée: Permissions all-or-nothing (impossible de granulariser)
- Onboarding difficile: Nouveaux devs perdus dans la complexité

Quand Découper: OUI si maintenabilité difficile, besoin tests unitaires, réutilisation staging↔prod, nouveaux devs perdus, bugs récurrents même zone. Découpe en priorité P2.

Solution - Architecture Recommandée 2025:
ops/
├── lib/ (bibliothèques réutilisables)
│   ├── core/ (logging.sh, colors.sh, utils.sh)
│   ├── docker/ (containers.sh, images.sh, compose.sh)
│   ├── database/ (backup.sh, restore.sh, migrations.sh)
│   ├── health/ (checks.sh, waiters.sh)
│   ├── deployment/ (blue_green.sh, rollback.sh, metrics.sh)
│   └── security/ (credentials.sh)
├── config/ (staging.env, production.env)
├── staging/ (deploy.sh orchestrateur 400 lignes max)
├── production/ (deploy.sh orchestrateur)
└── tests/ (tests unitaires par module)

Règles de Découpage Best Practices:
1. Taille maximale: 300 lignes par fichier (Google Style Guide 500, DevOps best practices 300)
2. Principe Responsabilité Unique (SRP): Un fichier = une responsabilité
3. Dépendances explicites: Déclarer dépendances en haut du fichier
4. Namespacing fonctions: Préfixer fonctions par module (db_backup_create, db_restore_from_file)
5. Documentation module: Header standardisé avec description, dépendances, version

Avantages du Découpage:
1. Maintenabilité +80%: Débugger fonction = éditer 1 fichier 250 lignes vs scroller 2700 lignes
2. Testabilité +90%: Tests unitaires par module isolés vs impossible avec monolithe
3. Réutilisabilité: Partager libs entre staging/production (DRY principle)
4. Performances: Lazy loading réduit startup time 2s → 0.3s
5. Sécurité: Permissions granulaires par module vs all-or-nothing

Migration Progressive (Refactoring sans Downtime):
- Étape 1 (Semaine 1, 2h): Extraire logging.sh
- Étape 2 (Semaine 2, 3h): Extraire docker.sh
- Étape 3 (Semaine 3, 4h): Extraire database.sh
- Étape 4 (Semaine 4, 8h): Tests unitaires complets
Total: ~20h sur 1 mois sans interrompre production

Comparaison Avant/Après:
- Lignes par fichier: 2700 → 150-300 (+85% lisibilité)
- Temps debug: 20 min → 3 min (-85%)
- Tests unitaires: Impossible → 15 fichiers (+100%)
- Réutilisabilité: 0% → 100% (Staging↔Production)
- Onboarding nouveau dev: 2 jours → 2 heures (-75%)
- Maintenance annuelle: 40h → 10h (-75%)

Pièges à Éviter:
1. Sur-découpage: Éviter trop granulaire (10 lignes par fichier), viser 150-300 lignes
2. Dépendances circulaires: Architecture en couches unidirectionnelles (core → database → deploy)
3. Paths relatifs cassés: Utiliser paths absolus depuis SCRIPT_DIR

Plan d'Action Priorisé:
- Semaine prochaine: Extraire logging.sh + docker.sh (quick wins)
- Mois prochain: Extraire database.sh + health_check.sh
- Trimestre: Tests unitaires complets

Cas d'Usage: Scripts déploiement > 1000 lignes, besoin tests unitaires fonctions critiques, réutilisation code entre environnements, équipes multiples, permissions granulaires sécurité.

Notes Opérationnelles: Migration progressive module par module, tests avant/après extraction, documentation dépendances, versioning modules, backward compatibility pendant transition.
